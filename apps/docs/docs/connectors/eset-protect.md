ESET PROTECT detections — antivirus, HIPS, firewall, network intrusion, web access and ESET Inspect rule hits — via the ESET Connect API, with the affected device resolved for its hostname, addresses and operating system. Read-only.

- **Connector id:** `eset_protect`

:::

## Setup

1. In the console, go to **Connectors → Add connector** and pick **ESET PROTECT**.
2. Fill in the fields above and run **Test connection**. The test is read-only and does not save anything.
3. Save. Polling starts on a jittered schedule within about a minute; the connector row shows `last_sync` once the first poll completes.

:::tip If `last_sync` stays empty
The first poll is the honest signal that the credential works. A connector that saves cleanly and never syncs usually means the credential lacks a scope the vendor requires for reads — check the connectors service log for the vendor's own error, which is passed through verbatim rather than summarised.
:::

## Getting the credential

ESET Connect signs in as a dedicated API user, not with an API key. ESET's
[Create a new API user](https://help.eset.com/eset_connect/en-US/create_api_user_account.html)
page walks through it:

1. Sign in to ESET PROTECT Hub (or ESET Business Account, or ESET MSP
   Administrator 2) as a Superuser.
2. Add a new user, give it read access to the companies whose detections you
   want, and turn on the **Integrations** toggle under **Permissions**
   (**Access Rights** in ESET Business Account).
3. Accept the invitation email, set the password, and **sign in to ESET
   PROTECT Hub once** with the new user. ESET refuses API calls from a user
   that has never signed in.
4. Enter that user's email and password in the connector, and pick the
   region your account lives in. The password is stored in the credential
   vault.

ESET doesn't let the Superuser (or the ESET MSP Administrator 2 Root user)
call the API, so the connector needs its own user.

## Regions

ESET Connect is served separately in each data region, and an API user only
exists in one of them. Pick the region your ESET PROTECT Hub or ESET
Business Account was created in:

| Region | Value | Hosts |
|---|---|---|
| Europe | `eu` | `eu.business-account.iam.eset.systems`, `eu.incident-management.eset.systems`, `eu.device-management.eset.systems` |
| Germany | `de` | `de.…` |
| United States | `us` | `us.…` |
| Canada | `ca` | `ca.…` |
| Japan | `jpn` | `jpn.…` |

There is no URL field. Every request goes to the chosen region's hosts over
HTTPS, so the credential is never sent anywhere but ESET.

## What is read

The connector signs in with an OAuth2 password grant at
`POST https://<region>.business-account.iam.eset.systems/oauth/token` and
uses the access token until shortly before it expires. If ESET refuses a
cached token early, the connector signs in once more; a freshly issued token
that is refused fails the poll instead of looping.

It then reads `GET /v1/detections` on the incident-management host, asking
for the poll window through `startTime` and `endTime`, 1000 detections a
page (the documented maximum). It follows `nextPageToken` until ESET returns
an empty one. If a later page fails, the pages already read are kept. If the
opening request is refused or can't reach ESET, the poll fails instead of
reporting an empty window.

Each detection becomes one alert: an antivirus or HIPS hit, a firewall or
network intrusion block, a blocked web page, a vulnerability or an ESET
Inspect rule match. The alert carries:

- the detection name as its title, and ESET's `circumstances` as its
  description;
- the category (`antivirus`, `hips`, `network_intrusion`, …), the object
  name, type and path or URL, and its SHA-1 and SHA-256;
- the process that triggered it and the user it ran as;
- for a network detection, the local and remote address and port, oriented
  by the direction ESET recorded (the remote peer is the source of an
  inbound connection);
- the actions ESET took, such as `cleaned by deleting`.

The whole vendor record is kept under `raw_event`.

**Each detection is raised once.** The poll window is applied to
`occurTime`, the moment the detection happened on the device. A detection
stamped after the read began is left to the next poll, whose window starts
where this one ended.

:::caution A device that was offline
ESET filters detections by when they happened, not by when ESET received
them. A device that was offline uploads its detections when it reconnects,
stamped with the time they happened. If that time falls in a window this
connector has already read, the detection isn't requested again. Keep the
poll interval short, and check the ESET PROTECT console for devices that have
been out of contact.
:::

## The host behind a detection

A detection names its device only by UUID. For the distinct devices in a
poll's detections, the connector calls `GET /v1/devices:batchGet` on the
device-management host, 50 devices a request. It lifts each device's
hostname (the console name if the system hostname is empty), its public
address and its operating system onto the alert, and keeps the device record
under `raw_event.device`. When a detection has no local address of its own,
the device's primary address stands in for it.

- A poll looks up at most 500 devices. When there are more, it logs
  `eset_protect.device_lookups_capped`.
- On HTTP 429, or a batch ESET is still preparing after its 120-second
  limit, the lookups stop early and `eset_protect.device_lookups_stopped` is
  logged.
- ESET answers a batch all or nothing, so a failed batch is logged as
  `eset_protect.device_lookup_failed`.

Every detection is still returned either way. The ones whose device wasn't
looked up arrive without a host.

## Slow answers

When ESET can't answer within 30 seconds it replies `202 Accepted` with a
`response-id` header and prepares the result in the background. The
connector waits five seconds and sends the same request again with that
header, until ESET returns the result. After its own 120-second limit ESET
gives up, and the poll fails with a message saying so. The next poll
retries.

## The severity ladder

| ESET severity level | AiSOC severity |
|---|---|
| `SEVERITY_LEVEL_HIGH` | `high` |
| `SEVERITY_LEVEL_MEDIUM` | `medium` |
| `SEVERITY_LEVEL_LOW` | `low` |
| `SEVERITY_LEVEL_INFORMATIONAL` | `info` |
| `SEVERITY_LEVEL_DIAGNOSTIC` | `info` |

ESET's ladder stops at high, so the connector never raises a detection as
`critical`. A detection at `SEVERITY_LEVEL_UNSPECIFIED`, or at any value ESET
doesn't document, carries no severity rather than a guessed one.

The ingest service files `eset_protect` events as OCSF 2001 Security
Finding, so every detection is promoted to an alert, whatever its severity.

## Troubleshooting

| Test connection or the poll says | Meaning |
|---|---|
| `… HTTP 400 to POST /oauth/token …` or `… HTTP 401 to POST /oauth/token …` | The email or password is wrong, the region isn't the one the account lives in, or the API user has never signed in to ESET PROTECT Hub. |
| `… HTTP 403 to GET /v1/detections …` | The user signed in, but it can't read detections. Turn on its **Integrations** toggle and grant it read access. |
| `… HTTP 202 … still preparing …` | ESET didn't finish preparing the result within its 120-second limit. The next poll retries. |
| `… HTTP 429 …` | ESET's API rate limit is used up, often by another integration using the same account. The next poll retries. |
| `… HTTP 503 …` | ESET is under maintenance. The next poll retries. |
| `ESET could not be reached at …` | The connectors service has no route to ESET. Check its outbound proxy and firewall rules for `*.eset.systems`. |
